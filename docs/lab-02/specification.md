# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

Build the Requester-facing TokTickIT ticketing MVP on top of the Lab 1 full-stack foundation. A selected Development Requester must be able to create a ticket, receive an official Ticket Number, view and manage their own tickets, inspect ticket details, and manage permitted attachments. The system must enforce ownership and provide consistent Zen Green responsive UI behavior.

---

## 2. Stakeholder Request Interpretation

The IT department needs a professional Requester-facing support system. Because real authentication will only be introduced in Lab 3, Lab 2 uses a Development Requester selector as a temporary testing identity. The selected Requester can create and view only their own tickets.

The application must provide Create Ticket, My Tickets, Ticket Detail, and Attachment workflows with validation, loading, success, failure, responsive, and empty states.

## 4. Functional Requirements

### Development Requester

- FR-01 The system shall retrieve active Development Requesters from PostgreSQL.
- FR-02 The Requester Selection screen shall display only active Requesters.
- FR-03 The user shall select one Development Requester before entering the ticket application.
- FR-04 The selected Requester shall be stored as the current testing context.
- FR-05 The application shell shall display the selected Requester's name.
- FR-06 The user shall be able to change the current Requester.
- FR-07 Changing the Requester shall reload Requester-specific ticket data.
- FR-08 If no Requester is selected, My Tickets and Ticket Detail shall not be accessible.
- FR-09 Inactive Requesters shall not appear in the selector.

### Create Ticket

- FR-10 The Requester shall be able to create a Ticket.
- FR-11 The Ticket shall contain Category, Related System, Summary, Description, and Requested Priority.
- FR-12 Requester shall be determined from the current Development Requester context.
- FR-13 Ticket Number shall be generated by the backend.
- FR-14 Ticket Date shall be generated by the backend.
- FR-15 Current Status shall be generated as New.
- FR-16 The frontend shall not generate or accept a client-defined official Ticket Number.
- FR-17 Successful creation shall return the created Ticket and official Ticket Number.
- FR-18 The UI shall display the official Ticket Number after successful creation.
- FR-19 Duplicate submission shall be prevented while the create request is processing.
- FR-20 If creation fails, entered form values shall remain available.

### My Tickets

- FR-21 The Requester shall be able to retrieve their own Tickets.
- FR-22 The ticket list shall support search.
- FR-23 The ticket list shall support filtering.
- FR-24 The ticket list shall support sorting.
- FR-25 The ticket list shall support pagination.
- FR-26 The ticket list shall display useful identifying information.
- FR-27 The list shall provide a meaningful empty state when the Requester has no Tickets.
- FR-28 The list shall provide a meaningful no-results state when a search/filter returns no Tickets.
- FR-29 Ticket results shall belong only to the selected Requester.

### Ticket Detail

- FR-30 The Requester shall be able to open one of their own Tickets.
- FR-31 Ticket information shall be displayed as read-only.
- FR-32 Ticket Detail shall display Ticket Number, Ticket Date, Requester, Category, Related System, Summary, Description, Requested Priority, Current Status, and timestamps where available.
- FR-33 A Requester shall not be able to retrieve another Requester's Ticket.
- FR-34 Ticket Detail shall provide Attachment management.

### Attachments

- FR-35 A Requester shall be able to add an Attachment to an owned Ticket from the Ticket Detail screen after the Ticket has been created.
- FR-36 Allowed Attachment types are JPG, JPEG, PNG, WEBP, and PDF.
- FR-37 Maximum Attachment size is 5 MB per file.
- FR-38 A Ticket may have at most five active Attachments.
- FR-39 Attachment metadata shall be stored.
- FR-40 Active Attachments shall be downloadable.
- FR-41 Removed Attachments shall not be downloadable.
- FR-42 Attachment removal shall be implemented as soft removal.
- FR-43 Removing an Attachment shall require a non-empty removal reason.
- FR-44 Removed Attachment metadata shall remain visible.
- FR-45 Attachment upload failure shall not make the Ticket disappear.
- FR-46 A Requester shall only manage Attachments belonging to their own Ticket.

## 5. Business Rules

- BR-01 The official Ticket Number is generated by the backend and must follow the format `TCK-YYYYMMDD-NNNN` (where `YYYYMMDD` is the UTC date of creation and `NNNN` is a 4-digit sequential zero-padded number), uniquely identifying the Ticket.
- BR-02 A newly created Ticket starts with Current Status `NEW`.
- BR-03 Ticket Date is generated by the backend as the UTC timestamp of creation.
- BR-04 The Requester associated with a Ticket is taken from the selected Development Requester context, communicated via the `X-Requester-Id` HTTP header.
- BR-05 A Ticket cannot be created without a selected active Development Requester.
- BR-06 The Development Requester selector is a testing mechanism and is not authentication.
- BR-07 Only active Development Requesters appear in the selector.
- BR-08 Changing the Development Requester changes the current testing context.
- BR-09 A Requester may retrieve only Tickets they own.
- BR-10 Ownership must be checked by the backend via the `X-Requester-Id` header, not only by the frontend.
- BR-11 Requester A must not be able to retrieve or modify Requester B's Ticket or Attachments. Unauthorized access attempts must return HTTP 404 (`{"error": "Ticket not found or access denied"}`) to prevent resource enumeration.
- BR-12 Category must be an active Category that exists in the database.
- BR-13 Related System must be an active Related System that exists in the database.
- BR-14 Summary is required and must contain 5–200 characters after trimming.
- BR-15 Description is required and must contain 10–2000 characters after trimming.
- BR-16 Requested Priority is required and must be one of `LOW`, `MEDIUM`, or `HIGH`.
- BR-17 Leading and trailing whitespace must be removed before storing Summary and Description.
- BR-18 Client-side validation provides immediate feedback, but backend validation is authoritative.
- BR-19 Submit must be disabled while a Ticket creation request is processing.
- BR-20 A failed Ticket creation request must not clear valid user-entered form values.
- BR-21 Search is case-insensitive and searches Ticket Number and Summary.
- BR-22 Ticket lists are returned in descending Last Updated order by default.
- BR-23 Ticket list pagination starts at page 1.
- BR-24 Permitted page sizes are 10, 20, and 50. The default page size is 10.
- BR-25 Invalid pagination, sorting, or filter parameters return HTTP 400.
- BR-26 Allowed Attachment types are JPG, JPEG, PNG, WEBP, and PDF.
- BR-27 Maximum Attachment size is 5 MB per file.
- BR-28 A Ticket can have no more than five active Attachments (`removedAt IS NULL`).
- BR-29 Attachment filenames must be sanitized before storage.
- BR-30 Attachment storage must not use a user-provided filename as the physical storage identifier (e.g. use UUID-based stored filenames).
- BR-31 Removed Attachments use a soft-removal field (`removedAt`) and are not physically deleted as part of the normal removal operation. Soft removal is performed via `DELETE /api/attachments/:id` with header `X-Requester-Id` and body `{"removalReason": "..."}`.
- BR-32 Removing an Attachment requires a non-empty removal reason string.
- BR-33 Removed Attachments remain visible as metadata but cannot be downloaded or previewed.
- BR-34 Only the owner of the Ticket may upload, download, or remove its Attachments.
- BR-35 Missing resources or unauthorized access attempts return HTTP 404 with a safe generic error response.
- BR-36 Unexpected server errors return a safe generic error message (HTTP 500) and must not expose stack traces or sensitive information.
- BR-37 When authentication is introduced in Lab 3, the `X-Requester-Id` header context will be replaced by the authenticated user identity session/token.

### Database Decisions

Unique constraints:

- DevelopmentRequester.email
- Category.name
- RelatedSystem.name
- Ticket.ticketNumber

Foreign keys:

- Ticket.requesterId
- Ticket.categoryId
- Ticket.relatedSystemId
- Attachment.ticketId

Indexes:

- Ticket.requesterId
- Ticket.updatedAt
- Ticket.categoryId
- Ticket.relatedSystemId
- Attachment.ticketId

Soft removal:

- Attachment.removedAt is NULL for active Attachments.
- Attachment.removedAt is non-NULL for removed Attachments.

## 9. Acceptance Criteria

### AC-01 Development Requester Selection

Given active Development Requesters exist, when the selector opens, then only active Requesters are displayed.

### AC-02 Requester Required

Given no Requester is selected, when the user attempts to enter the Ticket application, then the Requester Selection screen remains available.

### AC-03 Requester Switching

Given Requester A is selected, when the user changes to Requester B, then Requester-specific ticket data is reloaded for Requester B.

### AC-04 Create Ticket

Given valid Ticket data, when the Requester submits the form, then one Ticket is saved and the backend-generated Ticket Number is displayed.

### AC-05 Ticket Defaults

Given a Ticket is successfully created, then Ticket Date is generated by the backend and Current Status is `NEW`.

### AC-06 Validation

Given invalid Summary, Description, Category, Related System, or Requested Priority, when the form is submitted, then field-level validation messages are displayed and the API is not called.

### AC-07 Duplicate Submission

Given Ticket creation is processing, when the user clicks Submit again, then another creation request is not sent.

### AC-08 Create Failure

Given the Ticket creation API fails, when the error is returned, then a safe error message is displayed and entered form values remain available.

### AC-09 My Tickets Ownership

Given Requester A is selected, when My Tickets is opened, then only Requester A's Tickets are returned.

### AC-10 Search

Given the selected Requester has Tickets, when a valid search term is entered, then matching Ticket Number or Summary results are displayed.

### AC-11 Filtering

Given the selected Requester has Tickets, when a supported filter is selected, then only matching Tickets are displayed.

### AC-12 Sorting

Given multiple Tickets exist, when a supported sort option is selected, then Tickets are displayed in the requested order.

### AC-13 Pagination

Given more Tickets exist than the selected page size, when the user changes page, then the correct page of Tickets is displayed.

### AC-14 Empty State

Given the selected Requester has no Tickets, when My Tickets loads, then a meaningful empty state and Create Ticket action are displayed.

### AC-15 No Results

Given Tickets exist, when search or filters match no Ticket, then a meaningful no-results state is displayed.

### AC-16 Ticket Detail Ownership

Given Requester B is selected, when Requester B attempts to retrieve Requester A's Ticket, then the backend rejects the request with HTTP 404 ("Ticket not found or access denied").

### AC-17 Attachment Upload

Given an owned Ticket and a valid Attachment, when the Requester uploads it from the Ticket Detail screen, then the Attachment metadata is stored and displayed.

### AC-18 Invalid Attachment

Given an Attachment has an unsupported type or exceeds 5 MB, when the user attempts to upload it, then the upload is rejected with a clear error.

### AC-19 Attachment Limit

Given a Ticket already has five active Attachments, when another Attachment is uploaded, then the upload is rejected.

### AC-20 Attachment Download

Given an active Attachment belongs to an owned Ticket, when the Requester downloads it, then the file is returned.

### AC-21 Attachment Removal

Given an active Attachment belongs to an owned Ticket, when the Requester provides a non-empty removal reason and confirms removal, then the Attachment is soft-removed.

### AC-22 Removed Attachment

Given an Attachment has been soft-removed, when the Requester views the Ticket, then its metadata remains visible but download/preview is unavailable.

### AC-23 Attachment Ownership

Given an Attachment belongs to another Requester's Ticket, when the selected Requester attempts to access, download, or remove it, then the backend rejects the request with HTTP 404 ("Attachment not found or access denied").

### AC-24 Responsive UI

Given the application is viewed at desktop, tablet, and mobile widths, then the required screens remain usable without clipping, overlap, or horizontal page scrolling.

### AC-25 Accessibility

Given a keyboard-only user navigates the application, then controls have visible focus indicators, labels, and accessible names where required.

## 11. Assumptions and Decisions

1. Lab 2 continues from the Lab 1 TokTickIT repository.
2. Existing Lab 1 Category data and API are reused and extended where necessary.
3. Development Requester is a separate testing-context model and is not authentication.
4. Only one current Development Requester is active in the frontend session, communicated via `X-Requester-Id` header.
5. Ticket status begins at NEW and no later status workflow is implemented in Lab 2.
6. Requested Priority values are LOW, MEDIUM, and HIGH.
7. Search covers Ticket Number and Summary case-insensitively.
8. Default ticket sorting is Last Updated (`updatedAt`) descending.
9. Pagination uses page numbers starting from 1 with a default page size of 10 (permitted: 10, 20, 50).
10. Attachment maximum is five active files per Ticket, managed from the Ticket Detail screen.
11. Attachment size is limited to 5 MB per file with types JPG, JPEG, PNG, WEBP, and PDF.
12. Removed Attachment metadata remains in the database with non-empty removal reasons.
13. Backend ownership checks via `X-Requester-Id` are authoritative; unauthorized requests return HTTP 404.
14. Lab 3 will replace the Development Requester context with real authentication.
